## Money / AI / plans (invariants)

- ‼️ **A new paid model call = THREE things, not one:** a level in `_TIER_LIMITS` (`src/ai/usage.py`) + a freeze→tier→limit gate BEFORE the call + a usage record in `ai_usage` AFTER. Card translation lived without all three: a frozen tenant translated freely, the level had no limit. And **unlimited (`None`) on pro/business is unbounded spend**, because trial = Pro rights and sign-up on the site is self-service: `None` is allowed only on enterprise (contractual). The unit of the limit is one USER action (translating a description of 6 chunks = 1), and a cache hit charges nothing.
- ‼️ **Spend WITHOUT a human action is also gated by the subscription STATUS, not only by the plan.** Automatic analysis of the stream (`profiles.ai_analysis_level`) pays for every delivered tender on its own, so `src/ai/usage.py::auto_limit_decision` separates the axes: `status='active'` — the plan's monthly limit, `status='trial'` — the demo quota `TRIAL_AUTO_DEMO_LIMIT=10` for the WHOLE trial (not per month), any other status — refusal. The trial's Pro rights (`effective_tier`) deliberately do NOT apply here: sign-up is self-service, and "trial = Pro" on the automatic path would mean a paid stream for free. The levels allowed on the automatic path are listed in `src/domain/tiers.py::AUTO_ANALYSIS_LEVELS` (only `standard`); the gate sits in the WORKER (`src/workers/ai.py`), because a form is not the last line of defence: a POST can be sent by hand. A refusal of any kind → degradation to delivery without analysis, the tender is not lost.
- ‼️ **A refusal on a limit must be VISIBLE — "it silently turned off" is a defect, not a saving**. Three things for every limited level: (1) the remainder BEFORE the refusal — a counter in the cabinet (`ai_limits_service`, the "AI limits" block on `/cabinet/subscription`) and a caption on the button at the `_SOFT_LIMIT_FRACTION` threshold; (2) at the moment of refusal — a `.limit-flash` flash (CSS only: under the CSP `script-src 'self'` inline handlers silently do not work) with an upsell; (3) afterwards — a state in the button itself ("Limit used up → move to a higher plan"), because the flash disappears after ~6 s. The upsell is built by `src/plans/catalog.py::upsell_for_level`: the threshold comes from `_TIER_LIMITS`, the name and price from `CATALOG`, there is no third place with numbers. The guard is `tests/quality/test_limit_refusal_is_visible.py` (it collects ALL the `exhausted`/`demo_exhausted` points by predicate and requires a display path for each). ‼️ The flash only for a customer's ACTION and only about money: it must not appear on a model failure or a freeze, otherwise it stops meaning anything. In Telegram a pop-up alert is possible only BEFORE the first `callback.answer()` — it is already taken by the toast "⏳ Starting…", and Telegram will not show a second answer.
- ‼️ **A "grant/extend for N days" operation must be MONOTONIC.** `now() + days` in the "Extend access" button (`admin_service.grant_access`) once cut 11 days of paid access from a customer: the `manual` subscription was still valid, the operator pressed "3 days" — the expiry became shorter than the current one, the customer saw "2 days left". There is one canon for all sides: `src/domain/access.py::extend_until` (Python) + `extend_until_sql` (the SQL mirror) + SECURITY DEFINER `app_admin_extend_access` (0041, `GREATEST(COALESCE(access_until, now()), now()) + days` inside the UPDATE — the base is read in the same query, no extra SELECT and no race); the only call point for web/billing/bot is `src/domain/access_grants.py::extend_access`. **The billing webhook is a DIFFERENT contract:** `activated/renewed` sets the provider's ABSOLUTE `current_period_end` through `app_admin_grant_access`; do not touch it. Shortening the term is only through an explicit `revoke_access`. ‼️ `days=None` is not "unlimited" but an error: `GREATEST(...) + NULL = NULL` = silently granted eternal access, reject it before writing. Pass the "current expiry" argument WITHOUT a default value — otherwise a forgotten parameter brings the defect back silently.
- ‼️ **Disabling a subscriber = THREE axes, not one.** `revoke_access` moves only `tenants.access_until` — meanwhile the linked Telegram channel stays `active` (the bot answers the disabled user) and magic-link sign-in still works. A full disable is `app_admin_disable_subscriber` (0037): access + `user_channels → 'disabled'` + `users.deleted_at`. There is NO physical deletion in the product and none should be added: disabling is soft and reversible (`app_admin_enable_subscriber`). The exception is SELF-deletion from the cabinet (`account_delete_service`): the same three axes, but only for the user themself (the tenant — if they are the last one) + wiping email/phone/chat_id; it is irreversible, `app_admin_enable_subscriber` will not bring it back. The "access" axis gates content (`deps.require_active_access`), the `deleted_at` axis gates sign-in, including an already issued cookie.
- **Do NOT mix the plan axes:** the storefront `src/plans/catalog.py` ≠ the gating `src/ai/usage.py` `_TIER_LIMITS` ≠ the model choice `LEVEL_TIER`. ‼️ The axes have DIVERGED: `starter` exists in gating and in the CHECK but is not sold; `free` is allowed by `subscriptions_tier_check` and forbidden by `ck_tenants_tier`. The decision belongs to the product owner.
- **`src/ai/prompts.py` = behavioral code:** any PR that changes the file must be opened ONLY as `draft:true` + an A/B on live tenders before merging.
